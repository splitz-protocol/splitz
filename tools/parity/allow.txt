# Divergences between the two public surfaces that are idiom rather than gap.
#
# The Rust side of the comparison is `rust/splitz-core/src/lib.rs`'s `pub use` block — the
# names a consumer reaches as `splitz_core::…`. A name that is `pub` inside a module
# but not re-exported is not surface: the module is open, so it costs a
# consumer a compile error and a search, which is exactly what this lane is
# for. Dart's barrel re-exports its whole `src/`, so the two lists are
# comparable only when Rust's is taken from the crate root.
#
# Every line below states why a name exists on one side and not the other, or
# why two signatures differ. A line with no reason is a suppression, not an
# explanation, and this lane treats a stale entry as a failure so the list
# cannot outlive what it describes.

# --- names Dart has and Rust does not ---------------------------------------
dart::SplitCode          # Dart groups the refusal codes as static members of a class; Rust groups them as `pub const`s in the `code` module, which `rust::code` below records from the other side. The code strings themselves are identical and the corpus asserts all 77.
dart::raise              # Dart has no `Result`, so a refusal is a throw and `raise` is the one throw site. Rust returns `Err`, so there is nothing to name.
dart::VerifySignature    # Dart names the host's verifier as a typedef; Rust takes it as a generic `impl Fn`, which has no name to export.
dart::ConfirmationRule   # Dart names the §10.5 rule triple as a class; Rust returns it as a tuple from `confirmation_rule`, which both sides export.
dart::checkScalarValues  # §2.3's lone-surrogate check. Rust's `String` cannot hold a lone surrogate at all, so the check has no subject there and `serde_json` refuses the input one layer earlier.
dart::checkedBalance     # §5's symmetric balance bound, shared by `balances.dart` and `log.dart`. Hidden from the barrel; Rust's `checked_balance` is not re-exported from the crate root either.
dart::renderFiat         # §8.4's fiat rendering, shared by `zip321.dart` and `obligation.dart`. Hidden from the barrel; Rust's `render_fiat` is not re-exported from the crate root either.
dart::canonicalBytes     # §9.4's canonical base64url decode, shared by `authority.dart`, `serialization.dart` and `log.dart`. Hidden from the barrel; Rust's `unbase64url` is not re-exported from the crate root either.
dart::hasLoneSurrogate   # The predicate behind `checkScalarValues`, unreachable in Rust for the same reason.

# --- names Rust has and Dart does not ---------------------------------------
rust::Result             # The crate's `Result<T> = core::result::Result<T, SplitError>` alias. Dart throws, so there is no alias to name.
rust::code               # The module holding the refusal-code constants; Dart's counterpart is the `SplitCode` class above.
rust::Shares             # The typed shape `split_expense` returns. Dart returns `Map<String, int>` directly, which needs no name.

# --- signature shapes -------------------------------------------------------
# A parameter Dart types as `Object?` whose Rust counterpart is typed
# concretely. Rust cannot be handed the wrong type at all, so its CALLER has to
# decide first; Dart's callee decides. Each pair below was run against the same
# wrong-typed values in all three implementations and refuses with one code.
shape::check_currency parameter 0 is Object? code in dart and value: &str in rust   # a non-string reaches Dart's callee and is bill_bad_currency; in Rust `as_str()` fails at the call site and the fold sets the entry aside with the same code (§10.3). Run over an expense and a payment whose `currency` is an int, null, bool, list and object: fold OK, setAside=[bill_bad_currency], bill decodes, all three.
shape::is_currency parameter 0 is Object? code in dart and value: &str in rust      # the predicate behind check_currency; same pair, same reasoning.
shape::canonical_instant parameter 0 is Object? text in dart and text: &str in rust # a non-string is bill_type_error in Dart's callee and in the reference; in Rust the caller's `as_str()` fails first and raises bill_type_error too. Run over int, null, bool and a list.

dart::NothingMissing         # §14.5's three answers are a sealed class hierarchy in Dart and the three variants of one `enum Delta` in Rust. A Rust enum variant is not a crate-root name, so it has nothing to pair with; `Delta` itself is on both sides and is what a consumer names.
dart::DeltaSquare            # §14.5's three answers are a sealed class hierarchy in Dart and the three variants of one `enum Delta` in Rust. A Rust enum variant is not a crate-root name, so it has nothing to pair with; `Delta` itself is on both sides and is what a consumer names.
dart::TooBigForOneSquare     # §14.5's three answers are a sealed class hierarchy in Dart and the three variants of one `enum Delta` in Rust. A Rust enum variant is not a crate-root name, so it has nothing to pair with; `Delta` itself is on both sides and is what a consumer names.

shape::fold_log takes 3 in dart, 2 in rust   # Dart takes the host's verifier as an optional named parameter; Rust cannot, because `Option<impl Fn>` needs a turbofish at every call site that passes `None`. Rust therefore splits the two into `fold_log` and `fold_log_verified`, and `fold_log` calls the second with no verifier. Both are exported and the corpus runs the verified path in both implementations.
